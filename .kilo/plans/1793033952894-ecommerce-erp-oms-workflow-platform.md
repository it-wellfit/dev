## 1. 業務現場解構（三角色工作流）

### 1.1 現有人工流程（As-Is）

| 角色 | 現行工作 | 每日節奏 | 痛點根源 |
|------|---------|---------|----------|
| 行銷人員 | 產生產品企劃 → 人工到電商後台建活動、調價、上架 | 每天；活動檔期前爆量 | 活動設定繁瑣、跨系統重複輸入、價格錯誤無防護 |
| 業務人員 | 買賣填單（接單/出貨/調撥）→ 人工輸入 FlapsErp | 每天、高頻 | 訂單漏打、雙重輸入、庫存不同步導致超賣 |
| 財務人員 | 記帳、對帳（訂單 ↔ 金流 ↔ 撥款 ↔ 發票） | 每天記帳、月底對帳爆量 | 三方帳目人工核對、退款/折讓流程分散 |

### 1.2 目標流程（To-Be 核心原則）

1. **單一事實來源（Single Source of Truth）**：FlapsErp 為庫存與帳務主檔；電商訂單以自建電商 DB 為來源；金流以 Webhook 為付款結果唯一真實來源（證據：wasateam.com 金流串接指南 —「以後端 Webhook 為訂單狀態的唯一真實來源」）。
2. **事件驅動取代輪詢**：自建電商發事件 → OMS 中台消費 → 推 FlapsErp / 金流 / 物流。
3. **每一步皆冪等**：幂等鍵 = `{來源系統}:{單號}:{狀態}`，防重複扣庫存/重複開發票/重複退款（證據：foreverwebs 金流指南 踩雷1「webhook 重送要做 idempotency key」）。
4. **例外走人工複核佇列**，正常流全程無人。

### 2A.2 子系統重映射（v3 自建 → v4 原生優先處置）

| v3 子系統 | v4 處置 | 理由 |
|-----------|--------|------|
| S1 訂單同步引擎 | **改用原生**：自建電商以「官網商城」身份經 **FLAPS 標準 API** 直連平台訂單管理（訂單 push 進 FlapsErp）；同步頻率依官方規格（最短 5 分鐘輪詢，或我方主動 push 達成近即時） | 原生已實作多平台訂單聚合、狀態雙向同步、一鍵出貨；自建重複 = 造輪子 |
| S2 庫存防超賣 | **改用原生**：庫存即時連動扣減 + **回壓比例設定**（即本計畫研究的 channel allocation 概念，FlapsErp 已原生實作且可依平台毛利/檔期彈性配置）；多倉調撥原生支援 | 原生即研究文獻中的 best practice；原廠維護勝過自建 |
| S3 金流多閘道適配 | **金流仍掛自建電商端**（ECPay/NewebPay 適配器保留，v3 規格不變）；FlapsErp 原生「依付款方式自動生成應收帳款」接收結果 | 金流責任在電商端（收卡），ERP 端只做帳務——原生已涵蓋 |
| S4 自動對帳 | **主體改用原生自動沖帳**（平台抽成/撥款匯流、訂單自動轉拋會計科目、傳票拋轉——配合截圖之「匯入傳票」）；中台僅保留**三方差異報表**（原生對帳的可觀測性增強） | 原生已做 ERP 內兩方沖帳；「訂單↔金流↔撥款」跨廠商差異偵測仍值得補 |
| S5 促銷規則引擎 | **維持自建**（自建電商端促銷與價格護欄——FlapsErp 促銷為 POS/門市導向，自建官網端需要自己的規則引擎）；規則結果經 FLAPS API 同步 | 原生促銷不覆蓋自建電商結帳流程 |
| S6 RMA 售後引擎 | **入口改用原生**：平台退貨申請 API 自動寫入 FLAPS 退貨申請作業（原生已做，含「商品回倉後人工確認才轉正式退貨」的庫存保護設計）；中台補建 **SLA 看板 + 智慧分流規則 + 原因庫分析** | 原生管單據流，中台管時效與分析 |
| S7 FlapsErp 橋接 | **徹底改寫**：主通道 = **FLAPS 標準 API**（雙向，官方文件）；批次/備援 = Excel 匯入作業（RPA 驅動，含 Api/INS、OUT、SBK、CANCEL 單據接口——使用者提供麗嬰房產線證據）；winax/ffi-napi 降為最後手段 | 官方 API > UI 自動化；v3.2 的 Api/* 接口表與 Excel 21+ 作業清單全部保留為備援 |

**結論：自建範圍 51 人日 → 約 25 人日；工期 16 週 → 8–10 週；RSK 總分大幅下降（原生功能由原廠維護，含 ISO 27001 資安與每日備份）。**

## 5. 子系統規格

> **⚠️ v4 閱讀指引**：以下 S1–S7 保留 v3 完整規格作為**設計基準與兜底藍圖**；實作範圍依 §2A.2 重映射執行——S1/S2/S4 主體改用 FlapsErp 原生模組（原生已內建同等機制：回壓比例＝channel allocation、自動沖帳＝reconciliation、退貨申請作業＝RMA intake），S3/S5 全額保留自建，S6/S7 依 v4 處置縮減。若 OQ-14 授權盤點發現原生模組未訂閱且不加購，則該子系統退回 v3 自建規格（架構向下相容，兩版本規格均完整保留）。

### S1 訂單同步引擎（解 P1 訂單漏打）

- **輸入**：自建電商 Webhook `order.created/updated/cancelled`（主要）+ 每 15 分鐘 `GET /orders?since=last_cursor` 輪詢補漏（研究依據：exsited.com — webhook 涵蓋 ~98%，輪詢/對帧補 2–3% 漏失）。
- **狀態機**：`created → paid → reserved → shipped → delivered / cancelled / returned`（合法轉移表定義，非法轉移入例外佇列）。
- **冪等**：入庫前查 `idempotency(merchant_order_id, status)`；Outbox 模式 — 業務寫入與事件記錄同一交易（證據：GitHub settlement 範例 — Transactional Outbox + FOR UPDATE SKIP LOCKED claim）。
- ** Saga 補償**：扣庫存失敗 → 通知電商標記缺貨；金流失敗 → 釋放保留（對映 vps.do OMS Lifecycle 第 3–5 步）。
- **輸出**：寫 FlapsErp（經 S7）、發 `order.paid` 事件觸發 S2 保留庫存與 S5 活動統計。

### S2 庫存防超賣引擎（解 P2 超賣）

- **ATP 公式**：`可用 = on_hand − reserved − safety_stock`（證據：datadank.com 庫存同步系統設計；safety stock 依 SKU 周轉速度調整）。
- **保留機制**：下單即建立 `reservation(order_id, sku, qty, expires_at=+30min)`；付款成功 → 轉正式扣帳；逾期未付 → 定時掃描釋放（證據：exsited.com — reservation windows 30 秒~數分鐘，Black Friday 案例 127 次潛在超賣被攔截、成功率 99.97%）。
- **競態控制**：SQLite 條件更新 `UPDATE stock SET reserved=reserved+? WHERE available>=?`（原子性等效於研究中的樂觀/悲觀鎖取捨；高併發熱門 SKU 加 per-SKU 序列化處理，證據：tanhdev.com Kafka 分區鍵模式，此處以單機佇列分區等效實作）。
- **推播策略**：合併（coalescing）同 SKU 短時多次變動；優先推送「降庫存」更新（防超賣優先於防少賣，證據：datadank.com backpressure 章節）。
- **修漂移**：每日 03:00 三方對帧（FlapsErp 帳 ↔ 中台保留帳 ↔ 電商顯示），差異自動修正 + 告警；每筆「因缺貨取消」訂單回溯同步時間線定位根因（datadank.com oversell analysis）。

### S3 金流多閘道適配層（解 P5/P6）

- **統一介面** `IPaymentAdapter`：`createPayment(order)` / `handleNotify(payload)` / `queryTrade(tradeNo)` / `refund(refundReq)` / `querySettlement(date)`。
- **首發適配器**：
  - **ECPay 綠界**（主要）：ReturnURL/NotifyURL 背景通知、CheckMacValue 驗簽、回應 `1|OK`、TLS 1.2、API 節流（403 時停 30 分鐘，證據：developers.ecpay.com.tw 介接注意事項原文）；付款方式：信用卡、ATM 虛擬帳號、超商代碼/條碼、Apple Pay、TWQR。
  - **NewebPay 藍新**（次要）：Sandbox 與正式帳號完全分離、NotifyURL、LINE Pay 需後台另開通；ATM 退款僅「智慧 ATM 2.0」支援且需預先人工申請開通 + 結帳時收集買方銀行帳號（Source Type/SourceBankId/SourceAccountNo），退款 API 文件未公開需向客服索取（證據：oberonlai.blog 踩坑清單 6 條）。
- **鐵律**（全部來自研究，逐條可查）：
  1. Webhook 為付款結果唯一真實來源；前端跳轉僅供 UX（wasateam.com）。
  2. 每筆通知重算 CheckMacValue/簽章 + IP 白名單雙驗證。
  3. 冪等鍵防重送（foreverwebs 踩雷 1）。
  4. 後端重算金額，絕不信前端金額（wasateam 資安 5 條之 2）。
  5. 永不儲存卡號（PCI-DSS 由金流商承擔，server 只拿 token；foreverwebs 踩雷 6）。
  6. 保留原始回應 raw response 入稽核日誌 ≥ 7 年（爭議款舉證；foreverwebs 踩雷 3 + 交付清單）。
  7. 測試/正式參數分離並上鎖（最常見上線事故；onlinestore.com.tw、makewebsites.tw）。
  8. 退款矩陣先行測試：原卡退/帳戶退/部分退/跨日退，各金流規則不同（foreverwebs 踩雷 4）。

### S4 自動對帳引擎（解 P3 對帳耗時）

- **三方對帳（日批）**：`訂單(OMS) ↔ 金流交易(ECPay/藍新對帳檔/查詢API) ↔ 撥款報表`，鍵 = 訂單編號 + 金流交易編號 + 發票號 + 物流單號四鍵互查（證據：makewebsites.tw —「對帳時應至少能用訂單編號、金流交易編號、發票號碼與物流單號互相追查」）。
- **比對維度**：金額、狀態（已授權/已請款/已撥款/已退款）、手續費、時間窗（信用卡撥款 T+15 等週期表；證據：foreverwebs 清算速度表）。
- **差異分級**：金額差（高優先）、狀態差（中）、時間未到（自動延後重查）。差異 → 自動建工單入人工複核佇列 + 月底結帳前清零看板。
- **金流對帳檔**：每日排程自動下載（CSV/API），留存 7 年。

### S5 促銷規則引擎（解 P4 活動設定）

- **規則類型**：滿額/滿件/折扣/買 X 送 Y/N 件 M 折/組合價/贈品/會員分眾（證據：tonesky.com.tw 智慧促銷系統功能清單）。
- **四步發布流**：選活動類型 → 設條件（商品/會員/期間/通路，多條件 AND/OR + 優先序）→ **試算**（模擬購物車驗證折扣/稅額/總價）→ 發布 + 排程自動上下架（tonesky 使用流程四步原文）。
- **護欄**：最低售價紅線與毛利紅線 — 疊加後價格低於紅線即攔截或轉簽核（證據：jijiaerp 促銷 — 價格紅線/最低毛利試算；簡道云 — 毛利護欄、折扣越權審批）。
- **疊加規則**：活動間可併用/互斥/優先序設定，防「折上加折」事故（jijiaerp 疊加判斷/疊加明細）。
- **行銷自營運**：規則全配置化，行銷人員免工程介入；活動成效（使用次數/訂單金額/優惠成本/轉換率）自動歸集（旺店通規則引擎 + 費用歸集模式）。

### S6 RMA 售後流程引擎（解 P7 客訴退換貨）

- **統一入口**：官網表單 / LINE 官方帳號 / 出貨單 QR Code / 客服代建 — 全部進同一案件池（證據：oron.com.tw RMA 攻略 —「沒有統一入口，等於沒有案件管理」）。
- **自動分流規則引擎**（配置化非寫死）：瑕疵→品管、後悔→客服、物流損壞→倉管+通知物流商；金額門檻觸發分層簽核（ORON 模組二）。
- **標準節點與 SLA**（照表配置，證據：簡道云 RMA 流程表原文）：

| 節點 | SLA | 自動化動作 |
|------|-----|-----------|
| 資格校驗 | 15 分 | 依 SKU/時效/次數/狀態/黑名單自動判定 |
| 審批+RMA 號 | 2 小時 | 生成 RMA 單、鎖退款額度、推客戶寄回指引 |
| 物流寄回 | 1–3 天 | 面单生成、軌跡回傳、超時提醒 |
| 倉收貨 | 當天 | 掃碼簽收、明細/照片自動比對 |
| 質檢分級 | 24 小時 | 良品/次品/報廢模板、爭議升級通道 |
| 入庫/退款 | 當天 | 庫存回補、金流退款 API、電子發票折讓（2025 起 e-發票折讓憑證為主流） |
| 回訪歸檔 | 48 小時 | 原因標籤入庫、退貨率看板（依商品/供應商/物流/原因） |

- **聯動鐵律**：退貨入庫 ⇄ 退款觸發 ⇄ 發票折讓 ⇄ 會計分錄四者綁定，防「貨到了錢沒退/錢退了貨沒到」（hupun.com 售後誤區 3；oron 雷二：必須與 ERP 串接）。
- **風控**：高退貨率客戶提高憑證要求/人工審核；序列號綁定防調包。

### S7 FlapsErp 橋接層（API 主 + RPA 備援）

- **主通道（API/DB/COM）**：自建電商已開放 API —— 但注意：**FlapsErp 桌面端仍以 winax(COM)/ffi-napi(DLL)/檔案匯出為唯一通道**（v1/v2 逆向結論不變）。
- **⚠️ 雙向通道未證實（OQ-11 / RSK-16）**：「winax 可消費 COM」≠「FlapsErp 提供寫入介面」。registerDLL.ps1 所註冊之 DLL 屬性（官方整合 API 或第三方元件）必須於 W1 spike 釐清；**讀取**（庫存主檔匯出）與**寫入**（訂單/出庫單/庫存異動匯入）分別定通道，不得混為一談。
- **RPA 定位調整**：OpenRPA 不再是「對電商的 UI 自動化主力」，而是 (a) FlapsErp 無 API 覆蓋功能之操作備援（含 OQ-11 兜底之 UI 寫入）；(b) 桌面端 UI 冒煙測試工具。此調整將 RSK-01（UI 佈局變更）影響面大幅縮小，但 RSK-16 成立時 RPA 升級為寫入主通道。
- **庫存/帳務主檔同步**：FlapsErp 定期（≥每 5 分鐘）匯出庫存異動 → 中台套用；FlapsErp 記帳由對帳結果驅動（差異清零後自動產生傳票草稿，財務確認入帳）。
- **SKU 主檔對映**：中台維護 `sku_mapping` 表（電商 SKU ↔ FlapsErp 商品代碼 ↔ 條碼），由業務單位認領維護權；無對映之 SKU 下單 → 例外佇列（防幽靈庫存），不自動建檔。

## 8. 交付藍圖（v4 Native-First：10 週三期，較 v3 之 16 週壓縮）

| 期 | 週 | 內容 | 出口條件（可驗證） |
|----|-----|------|-------------------|

**範圍邊界明確化（納入層級）**：

| 項目 | 層級 | 說明 |

| 會員/CRM | 排除 | S5 僅消費會員等級欄位，不建 CRM |
