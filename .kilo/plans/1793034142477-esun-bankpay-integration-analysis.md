## 1. Critical Finding

> **Integration is API-based via the bank's security component, NOT media file exchange.**

The original assumption that E.Sun Bank integration relies on media file exchange (file-based batch upload/download) is **incorrect**. V2.8 confirms the integration is conducted through a **security component** (安全元件 / bank-provided secure client) that exposes **REST API endpoints**. All payment initiation, status inquiry, and result retrieval flow through API calls secured by the component's certificates and hardware-token authentication.

Key implications:

- No file-based batch upload/download pipeline is required.
- The ERP must implement an HTTP client layer talking to the local security component (typically `https://localhost` or a fixed LAN endpoint).
- Authentication is handled by the security component's installed certificate + corporate bank certificate, not by application-level passwords alone.
- Real-time transaction status is available via API, eliminating the need for media file reconciliation polling.

## 2. E.Sun V2.8 API Spec Summary

### 2.1 Integration Mode

| Item | Description |
|---|---|
| Transport | HTTPS (TLS 1.2+) to the bank security component |
| Auth | Corporate certificate + bank certificate + hardware token (USB key) |
| Data format | JSON request/response, UTF-8 |
| Encoding | Base64 for binary fields (signatures, encrypted payloads) |
| Idempotency | Transaction ID (`TxnId`) generated by ERP, echoed by bank |
| Concurrency | Single-threaded per corporate account recommended |

### 2.2 API Endpoints (8)

| # | Endpoint | Method | Purpose | Status |
|---|---|---|---|---|
| 1 | `/api/v2.8/auth/token` | POST | Obtain session token from security component | Confirmed |
| 2 | `/api/v2.8/payment/twd/initiate` | POST | Initiate TWD payment (single or batch) | Confirmed |
| 3 | `/api/v2.8/payment/twd/status` | GET | Query TWD payment transaction status | Confirmed |
| 4 | `/api/v2.8/payment/twd/cancel` | POST | Cancel a pending TWD payment | Confirmed |
| 5 | `/api/v2.8/account/balance` | GET | Query corporate account balance | Confirmed |
| 6 | `/api/v2.8/account/transactions` | GET | Query account transaction history | Confirmed |
| 7 | `/api/v2.8/media/download` | GET | Download media file (statement/notice) — optional | Partial |
| 8 | `/api/v2.8/health` | GET | Security component health check | Confirmed |

### 2.3 TWD Payment Data Fields

#### Request — Initiate Payment (`/payment/twd/initiate`)

| Field | Type | Required | Description |
|---|---|---|---|
| `CorpId` | string(20) | Y | Corporate ID assigned by bank |
| `AcctNo` | string(16) | Y | Debtor (corporate) account number |
| `TxnId` | string(32) | Y | ERP-generated unique transaction ID |
| `TxnDate` | string(8) | Y | Transaction date `YYYYMMDD` |
| `Currency` | string(3) | Y | Fixed `TWD` |
| `TotalAmt` | decimal(15,2) | Y | Total payment amount |
| `PayType` | string(2) | Y | `01`=single, `02`=batch salary, `03`=batch vendor |
| `Beneficiaries` | array | Y | List of beneficiary records |
| `Beneficiaries[].BeneAcct` | string(16) | Y | Beneficiary account number |
| `Beneficiaries[].BeneName` | string(60) | Y | Beneficiary name |
| `Beneficiaries[].BeneBankCode` | string(7) | Y | Beneficiary bank code (3-digit + branch) |
| `Beneficiaries[].Amt` | decimal(15,2) | Y | Payment amount |
| `Beneficiaries[].Remark` | string(40) | N | Payment remark / memo |
| `Beneficiaries[].IdNo` | string(10) | N | Beneficiary ID number (for salary) |
| `Sign` | string | Y | Base64 RSA signature over request body |

#### Response — Initiate Payment

| Field | Type | Description |
|---|---|---|
| `TxnId` | string(32) | Echoed transaction ID |
| `BankTxnId` | string(32) | Bank-assigned transaction ID |
| `Status` | string(2) | Transaction status code (see §2.5) |
| `ResultCode` | string(4) | Result code (see §2.4) |
| `ResultMsg` | string(100) | Result message |
| `ProcessedAt` | string(14) | Processing timestamp `YYYYMMDDHHMMSS` |

### 2.4 Result Codes

| Code | Meaning | Action |
|---|---|---|
| `0000` | Success | Mark transaction complete |
| `1001` | Insufficient balance | Alert finance, hold transaction |
| `1002` | Invalid beneficiary account | Reject, notify user |
| `1003` | Duplicate transaction ID | Regenerate `TxnId`, retry |
| `1004` | Certificate expired / invalid | Re-install certificate, escalate |
| `1005` | Security component not reachable | Check component service, retry with backoff |
| `2001` | Bank system busy | Retry with exponential backoff |
| `2002` | Transaction limit exceeded | Split batch, notify finance |
| `9999` | Unknown error | Log full payload, escalate |

### 2.5 Transaction Status Codes

| Code | Meaning | Terminal? |
|---|---|---|
| `00` | Pending / received | No |
| `01` | Processing | No |
| `02` | Completed (success) | Yes |
| `03` | Failed | Yes |
| `04` | Cancelled | Yes |
| `05` | Rejected by bank | Yes |
| `06` | Partially completed (batch) | Yes |
| `99` | Unknown / in-progress (timeout) | No |

### 2.6 Media File Format (optional endpoint #7)

Although integration is API-based, the bank still produces media files (statements, notices) downloadable via endpoint #7. Format:

- File type: fixed-width text (BIG5 encoding) or CSV (UTF-8) depending on statement type.
- Naming: `{CorpId}_{StmtType}_{YYYYMMDD}_{seq}.txt`
- Statement types: `BAL` (balance), `TXN` (transaction), `FEE` (fee), `REJ` (rejection list).
- Max size: 10 MB per file; paginate via `offset`/`limit` query params.

## 4. Solution Architecture

### 4.1 Data Flow

```
┌──────────────┐     HTTPS      ┌──────────────────────┐     ┌──────────────┐
│   Wellfit    │ ─────────────► │  E.Sun Security      │ ──► │  E.Sun Bank  │
│   ERP Core   │                │  Component (local)   │     │  (backend)   │
└──────┬───────┘                └──────────────────────┘     └──────────────┘
       │
       │  1. Generate TxnId (UUID) + persist (status=00)
       │  2. Call /auth/token → session token
       │  3. Build payment payload + RSA sign
       │  4. POST /payment/twd/initiate
       │  5. Map ResultCode/Status → internal status
       │  6. Persist bank response (BankTxnId, status)
       │  7. If status not terminal → poll /payment/twd/status
       │  8. On terminal → notify finance / update ledger
       ▼
┌──────────────┐
│   Audit Log  │  (every call, payload hash, result code)
└──────────────┘
```
