## 2. 決策記錄（每項：選擇／原因／替代／證據／風險）

### D-OCR1（v1.1 修訂，2026-11-10 使用者裁決）：**內嵌 PaddleOCR PP-OCRv5（ONNX）為預設引擎**——開箱即用，零外部安裝
- **使用者裁決**：「tesseract 不在本機」＋「務必採用最佳強大完整的解決方案」——外部自裝方案撤回；精度目標＝中英必備、趨近 100%、多格式。
- **選擇**：`paddle-ocr-rs 0.6.1`（Apache-2.0、26K 下載、PP-OCRv5 mobile 模型範例實證）承載推論管線；**PP-OCRv5 mobile ONNX 模型（det/cls/rec ≈16MB）以 NSIS resources 捆包**——安裝即含中文辨識能力。
- **原因**：① PP-OCRv5 為中文＋英文混合辨識的現行最強免費引擎（PaddleOCR 官方，Apache-2.0）② ONNX Runtime 路線＝stable 工具鏈相容（無 nightly／無 C++ 外部執行檔）③ 模型檔與 crate 解耦——精度升級＝換模型檔，不必改碼 ④ 每附件/圖片逐張推論，符合既有 fail-closed 逐列語意。
- **替代**：`paddleocr_rs_onnx 0.2.8`（MIT、2026-10-22 更新、DirectML GPU 加速、方向分類內建）——備選引擎（若 paddle-ocr-rs 實測不佳即換）；`ocrs 0.14.0`——**官方 README 明示「recognizes the Latin alphabet only」＋自評 early preview → 中文不符，出局**（事實終結 ocrs 線）；`franken_ocr`——**nightly 工具鏈與工作區 stable 憲政衝突，出局**；外部 tesseract.exe——使用者裁決撤回。
- **證據**：crates-io（paddle-ocr-rs 0.6.1/26K dl；paddleocr_rs_onnx 0.2.8；ocrs README 原文引述）；PP-OCRv5 為 PaddleOCR 官方最新世代。
- **精度誠實聲明**：乾淨列印中文 PP-OCRv5 達 ~97-99% 字元準確率；「100%」在任意輸入（手寫/傳真/低光照片）上無引擎可保證——**本產品以置信度閘＋人工確認吸收殘差**（fail-closed 既有架構），此即「趨近 100% 的完整解」的工程定義。
- **模型取得**：PP-OCRv5 mobile ONNX 自 PaddleOCR 官方匯出（paddle2onnx）或 RapidOCR 模型庫；放置 `resources/models/ocr/`（NSIS resources 捆包）；缺失 → 偵測式降級訊息（保留原骨架）。
- **風險**：模型檔使安裝器 +16MB（可接受）；paddle-ocr-rs crate 10 個月未更新（API 穩定風險低，模型解耦；必要時換 paddleocr_rs_onnx）。**低-中**。

### D-OCR2：掃描式 PDF 偵測採零新依賴啟發；pdf-inspector 列強化候選
- **選擇**：`extract_text_from_mem` 成功但有效字元數 < 閾值（初定每頁 < 20 非空白字元）→ 判「疑為掃描式」→ 明確錯誤＋OCR 引導。
- **原因**：零新 dep；誤判成本低（引導訊息對兩態都合理）。
- **替代**：`pdf-inspector`（正規分類器，1.39M dl）——累積真實樣本後依誤判率決定更換。
- **風險**：文字極少的正常 PDF 被引導去 OCR（低損）。**低**。

### D-OCR3：影像原料（拍照）直送 OCR，無前處理；輸出以 `--psm 6`＋TSV 置信度解析
- **選擇**：accept 加 `.png/.jpg/.jpeg`；tesseract `-l chi_tra+eng --psm 6 tsv`；word-level 置信度按座標行重建 → 行文字 → 既有分隔啟發鏈；**行平均置信度 < 閾值（初定 60）→ 該列轉 error 並註明「低置信度，請人工核對」**。
- **原因**：fail-closed 精神——低置信不冒充合格列；人工經手是帳務底線。歪斜校正/二值化列精度調優項（tesseract 內建基本處理先跑）。
- **風險**：中文字符 OCR 精度波動（尤其手寫／傳真）——置信度閘＋人工核對吸收。**中**。

### D-EML1：V3-A 採 `mail-parser`＋附件**遞迴進料**
- **選擇**：`.eml` 上傳 → mail-parser 解析 → 附件逐一**遞迴走 detect_import_format**（csv/xlsx/pdf/影像各自轉接器）→ 每個附件一個獨立 import batch（sha256 逐檔記載，追溯性）。
- **原因**：遞迴讓「郵件」不是新格式而是**格式的載體**——管線零特例；每附件獨立批次＝既有審計模型直接沿用。
- **邊界**：附件數量上限（10）、單附件 2MB 沿用、MIME 白名單（csv/xlsx/pdf/png/jpg）、無附件 → 明確訊息。.msg 列次項。
- **風險**：巢狀附件（eml in eml）——首發僅一層（明示限制）。**低**。

### D-MAP1：V3-B 採「簽名自動匹配＋單次映射表單」兩態流程
- **選擇**：CSV/XLSX 解析後，首列同步標準 6 欄 → 現行直通；不符 → **映射頁**（零 JS 表單：每欄下拉選 target field 或「忽略」；以同義詞表自動猜測預填）→ 提交帶 mapping → 重跑 normalize → 既有 preview/confirm。
- **儲存**：映射 profile 存 `erp_config`（category=`ingest_profile`，key=來源簽名 sha256 短碼，value=JSON）；命中即自動套用（跳過映射頁）。升級路徑：量大遷 `ingest_profiles` 表。
- **原因**：不以互動式中間步驟侵蝕既有兩階段語意（映射是 normalize 的前置，仍不觸帳）；profile 讓重複來源一次設定永久免調。
- **同義詞表（初版）**：date←`date,日期,交易日期,傳票日期,日期時間`；debit←`debit,借方,借方科目,付方`；credit←`credit,貸方,貸方科目,收方`；amount←`amount,金額,價稅合計,應付金額`；currency←`currency,幣別,幣種`；description←`description,摘要,說明,備註,品名`。
- **風險**：猜測失準 → 使用者改下拉即可（失敗成本低）。**低**。

## 3. 架構設計

### 3.1 管線（最終形）

```
上傳（multipart）
  └─ detect_import_format（magic bytes）
      ├─ CSV/TSV ─┐
      ├─ XLSX ────┤
      ├─ PDF ─────┤→ cells[][] ─→ [V3-B 映射正規化] ─→ validate_fields ─→ drafts/errors ─→ PRG
      ├─ EML ─────┤      ↑                                              （既有二階段）
      │   └─ mail-parser → 附件逐一遞迴（上限 10）──────┘
      └─ PNG/JPG ─→ [V2.5 OCR：tesseract 外部＋TSV 置信度] ─┘
                     ▲ 可用性探測失敗 → 明確降級訊息（不進 errors 假列）
```

### 3.2 OCR 模組（V2.5）

- `ocr::is_available(state) -> OcrAvailability`（探測 exe 路徑＋執行 `--version` 成功；derive 非快取）
- `ocr::image_to_lines(data: &[u8]) -> Result<Vec<(String, f64)>, String>`（回傳行文字＋平均置信度）
- import_preview 新分支 `ImportFormat::Image`：非圖片 magic → Csv 為 fallback 的順序延伸（PNG=`89 50 4E 47`, JPEG=`FF D8 FF`）
- `/admin/api/net` 面板新增一列「OCR 引擎：可用（版本）／未安裝（引導訊息）」

### 3.3 映射模組（V3-B）

- `ingest::synonym_match(headers: &[String]) -> Vec<Option<Field>>`（同義詞表）
- `ingest::signature(headers: &[String]) -> String`（排序後欄名 join → sha256 短碼）
- import_preview 流程：解析 cells → 首列簽名命中 profile → 套用；否則若同義詞全命中 → 直接套用並提示「已自動對應」；部分/零命中 → 映射頁（PRG-to-self 帶 pending batch id）
- 映射結果套用後才進 validate_fields（資金欄位驗證仍在最後一關——不可繞）

### 3.4 Email 模組（V3-A）

- `eml::extract_attachments(data: &[u8]) -> Result<Vec<(filename, bytes)>, String>`
- preview 流程：eml 分支 → 附件清單 → 依序為每個附件建 batch（回報多 batch 摘要頁——既有 import 頁擴充「本郵件產生 N 個批次」區塊）
- 附件零位元組／超限／白名單外 → 逐項明確錯誤

## 4. 失敗模式與誠實邊界（UNKNOWN≠PASS）

| 情境 | 行為 |
|------|------|
| tesseract 未安裝 | 圖片上傳 → 明確訊息「OCR 引擎未安裝；處理方式：安裝 Tesseract 或聯絡管理員」；PRG 回匯入頁 |
| 掃描式 PDF（無文字層） | 「疑為掃描式 PDF（每頁有效字元 < 閾值）；處理方式：改用 OCR 流程或提供文字層檔案」 |
| OCR 低置信度行 | 該列 error＋「低置信度（avg 42），請人工核對」；不進入合格列 |
| EML 無附件 | 「郵件解析成功但無可匯入附件（支援 csv/xlsx/pdf/圖片）」 |
| EML 巢狀 eml | 首發不展開；明確訊息（限制聲明） |
| 映射未完成 | 映射頁停留（不進 preview）；欄位對應缺必要項（date/amount/…）時標示必填 |

## 5. 資安與資源

- OCR：子行程呼叫（無 shell 拼接——`Command::new(path).arg(...)`）；輸入檔案大小沿用 2MB 上限；超時（20s）強制終止（防掛死）。
- EML：不落檔解壓（附件 bytes 直通）；附件數/大小/MIME 三重上限；檔名不信任（僅顯示＋sniff magic，不依副檔名路由）。
- 映射：mapping JSON 僅含欄位索引與枚舉名；所有值仍經 auto-escape 與 validate_fields。
- 資源：OCR 為 CPU 密集——偵測可用性＋單請求超時；併發限制沿用現行單體（無 async 池爆走）。

## 6. 驗收規格（雙態測試策略——CI 無外部依賴仍可綠）

| 期 | 驗收（指令級） |
|----|----------------|
| V2.5 | ① 無 tesseract 環境：`import_image` 測試斷言**明確降級訊息**且 PRG 回匯入頁 ② 有 tesseract 環境（標記型測試）：合成 PNG（程式繪字）→ OCR → 行 → draft（列數與欄位斷言） ③ 掃描式 PDF fixture（無文字層＋影像）→ 引導訊息 ④ `/admin/api/net` 顯示 OCR 狀態列 |
| V3-A | 手構 .eml fixture（MIME multipart，含 1 個 CSV 附件）→ 上傳 → 附件批次 draft 正確、sha256 記載；無附件 .eml → 明確訊息；超 10 附件 → 上限訊息 |
| V3-B | 亂序＋中文標題 CSV fixture → 首列同義詞自動對應（斷言 3 列 draft 欄位正確）；未知名稱欄 → 映射頁 → 表單提交 → preview；profile 命中 → 直通 |

## 7. 分期與依賴

1. **V2.5-a**：OCR 探測＋降級＋`/admin/api/net` 列（無 tesseract 也能交付，先立誠實骨架）
