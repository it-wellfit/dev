# ADR-0011-语言分工与多语言整合

## 狀態
Accepted

## 決策者與日期
Kilo 開發代理，2026-10-28

## 背景與問題陳述
工作區包含 ekpi-platform、Wellfit、SyncMesh 三個 Rust 工作區，憲章規定 Rust-first 與架構簡潔，避免引入不必要的微服務與複雜事件架構。同時，開發者詢問 Zig、Mojo、Hylo、Austral、Carbon、P、Valen、Triton、Gluon、Dogwood 等新一代系統語言與 AI 專用語言是否應導入工作區。需要明確語言分工，避免在一般應用邏輯中混用多語言，並建立「各司其職」的整合邊界。

## 考慮的選項與比較

### 選項 A：僅採用 Rust（推薦，已採用）
- 優點：工作區三專案均為 Rust，toolchain 已統一於 1.99.1，工具鏈與生態系成熟，符合憲章架構簡潔原則。
- 缺點：對 C FFI 與異質硬體 AI 加速場景支持有限。

### 選項 B：在一般應用邏輯中混用多語言（否決）
- 優點：可利用各語言特定優勢。
- 缺點：違反架構簡潔，增加建置與維護複雜度，工具鏈碎片化，違反「證據優先」與「本機優先」。

### 選項 C：Rust 為主，Zig/Mojo/TLA+ 作為視需求導入的補充（已採用）
- 優點：Rust 承擔一般應用邏輯；Zig 僅於 C FFI/嵌入式場景；Mojo 僅於 AI 異質硬體運算；TLA+ 僅於設計層形式化驗證；Hylo/Valen 僅概念研究。各司其職，不跨類比較一般應用程式效能。
- 缺點：未來導入 Zig/Mojo 時需建立 FFI 邊界與獨立建置流程。

## 決策與理由
1. Rust 為唯一一般應用實作語言，三專案繼續使用 Rust 工作區。
2. Zig 僅於未來需 C 語庫互操作或嵌入式目標時導入，透過 FFI 邊界與 Rust 連接，不混用於一般商務邏輯。
3. Mojo 僅於未來需 AI 模型推論內核或異質硬體加速時導入，另列「AI 與異質硬體運算」分組，不與 Zig 比較一般應用程式效能。
4. Triton 與 Gluon 不直接與 Zig 比較一般應用程式效能，僅於專項 AI 內核或 AI Agent 安全場景評估。
5. Hylo 與 Valen 僅作概念研究，不進入版本控制源代碼，因缺乏公平基準測試證明其整體優越，且工具鏈尚未成熟。
6. 建立 ADR-0011 記錄語言分工，嚴禁在一般應用邏輯中混用多語言。

## 結果與影響
正面：
- 工具鏈保持 Rust 單語言，MCP 層（cratesio/rust-analyzer/rust-mcp/narsil）繼續以 Rust 為核心，無碎片化。
- 建置流程分離：cargo / zig / mojo / tlc 各自獨立，僅在交付物層級組合。
- 符合工作區憲章「架構簡單、證據優先、本機優先」原則。

負面：
- 未來導入 Zig/Mojo 時需額外維護 FFI 邊界與獨立建置腳本。

風險：
- Hylo/Valen 設計理念先進但工具鏈未成熟，不得誤認為已勝過 Rust/Zig。
- Mojo 單一供應商（Qualcomm 收購 Modular），長期治理需觀察。
