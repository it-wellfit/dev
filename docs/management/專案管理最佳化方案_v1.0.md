## 3. 治理模型（Governance Model）

### 3.1 三條鐵律（Iron Rules）

1. **證據先行（Evidence First）**：任何能力宣稱必須指向一個測試 ID、一個可執行命令、或一份來源快照；缺一即不合格（引自 Knowledge/traceability/claims-vs-evidence.md 規則 1）。
2. **閘門強制（Gate Enforcement）**：P0 → P1 → P2 → P3 各閘門未通過不得進入下一階段；閘門以 CI 自動化（fmt/clippy/test）為主，文件審查為輔。
3. **版本真相（Single Source of Truth）**：每個專案僅一份現行文件；舊版標 Superseded 或移入 `archive/`；文件 status 欄位強制。

### 3.2 專案類型分類（Project Type Classification）

| 類型 | 定義 | 管理強度 | 範例 |
|---|---|---|---|
| **P（Product）** | 對外交付、有 KPI 與 SLA | 全套：閘門、CI、UAT、上線、監控 | EKPI、Wellfit（生產） |
| **R（Research）** | 技術偵查／PoC／原型 | 輕量：時間盒、期望產出、退出規則 | Flaps root、re-toolchain experiments |
| **N（New Initiative）** | 新專案啟動、需求未定 | 啟動包：OQ 登記冊、憲章、WBS | RPA-ECOM |
| **X（Maintenance）** | 已上線、維護模式 | SLO 監控、變更控管、季度回顧 | SyncMesh（維運） |

### 3.3 生命週期階段與閘門（G0–G6）

| 階段 | 名稱 | 退出條件（可驗證） | 證據要求 | 否決標準 |
|---|---|---|---|---|
| G0 | 啟動（Initiation） | 專案憲章簽核；OQ ≥ 80% 回覆；範圍確認單 | 簽核文件、OQ 登記冊 | 無 owner、無 due date |
| G1 | 需求（Requirements） | FRS 簽核；FR/NFR/MoSCoW 定稿 | FRS、claims-vs-evidence | 需求無驗收標準 |
| G2 | 設計（Design） | 架構文件；ADR 簽核；SEC 簽核 | ADR、架構圖、介面矩陣 | 高風險設計未處理 |
| G3 | 開發（Development） | 程式碼入庫；單元測試覆蓋率 ≥ 80%；無 Severity 1 缺陷 | PR + CI 綠燈 | clippy/fmt fail |
| G4 | 測試（Testing） | 整合測試報告；效能/安全達標；UAT 簽核 | 測試報告、簽核單 | 差異率 > 0.5% |
| G5 | 部署（Deployment） | 生產環境建置；回滾演練通過；監控啟動 | 部署紀錄、監控設定 | 無回滾計畫 |
| G6 | 結案（Closure） | 移交文件完整；維運簽收；知識沉澱 | 結案報告、Knowledge 條目 | 遺留未移交項目 |

**閘門檢查表模板**：見附錄 T-03。

### 3.4 豁免機制

R 型專案可申請「輕量模式」：只需 G0（憲章）→ G3（PoC）→ G6（結案），跳過 G1/G2/G4/G5。申請需在 `decisions/ADR-XXX.md` 記錄理由與退出條件。Flaps root 已屬 R 型，應補申請。

## 4. 進度與進展追蹤（Progress Tracking）

### 4.1 單一狀態帳本（Single Status Ledger）

所有專案狀態統一存放於 `docs/management/status_ledger.csv`（UTF-8 BOM，Excel 直開），欄位：

```
專案ID, 專案名稱, 類型, 階段, 進度%, 風險燈, 阻礙, Owner, 下一里程碑, 里程碑日期, 最後更新
```

**規則**：進度 % = 已完成 WBS 人日 ÷ 已核可的總 WBS 人日（禁止主觀估計）。每週五 16:00 前更新；未更新之專案自動標 🔴。

### 4.2 EVM-lite（Earned Value Management 精簡版）

| 指標 | 公式 | 目標 | 範例（RPA-ECOM 第 1 週） |
|---|---|---|---|
| PV（計劃價值） | Σ 計劃完成人日 | 3 人日 | M1 需求斂集 |
| EV（已獲得價值） | Σ 實際完成人日 | 3 人日 | 若完成 → EV=3 |
| SPI（進度績效） | EV / PV | ≥ 0.95 | 1.0 |
| CPI（成本績效） | EV / AC | ≥ 0.95 | AC=3 → 1.0 |
| EAC（完工估算） | AC + (BAC − EV) | ≤ BAC + 10% | — |

### 4.3 節奏（Cadence）

| 頻率 | 活動 | 產出 | 負責 |
|---|---|---|---|
| 每日 | Stand-up（非同步留言） | 阻礙清單 | DEV/QA |
| 每週一 | 週同步會（1h） | 進度回顧、風險更新、本週計畫 | PMT |
| 每週五 | 狀態報告 + 帳本更新 | status_ledger.csv、週報 | PMT |
| 每月 | 月度進度報告 | 里程碑達成、預算消耗、重大風險 | PMT |
| 每季 | 組合審查會（QBR） | OKR 檢討、資源重新分配、技術債決策 | 全員 |
| 每閘門 | Gate Review | 閘門證據包、Go/No-Go | PMT/ARCH/QA |

### 4.4 進度燈定義

| 燈 | 條件 |
|---|---|
| 🟢 綠 | SPI ≥ 0.95 且無阻礙 |
| 🟡 黃 | SPI 0.85–0.95 或有 minor 阻礙 |
| 🔴 紅 | SPI < 0.85 或有 critical 阻礙（外部依賴延遲、技術阻塞） |

## 5. 開發流程與工作流程拆解（Development Process & Task Decomposition）

### 5.1 標準開發流程（7 步）

```
1. 需求確認 → 2. 任務拆解（WBS）→ 3. 設計（ADR if needed）→ 4. 開發（TDD）→ 
5. Code Review → 6. CI 閘門（fmt/clippy/test）→ 7. 合併/發布
```

### 5.2 任務拆解規則（Task Decomposition Rules）

| 規則 | 說明 | 範例 |
|---|---|---|
| 單一任務 ≤ 1 人日 | 超過則拆分 | "MOD-02 OpenRPA 工作流開發 12 人日" → 拆為 12 個 ≤1 日任務 |
| 每任務必含：ID、名稱、父代號、預估人日、開始/結束、負責人、交付物、驗收命令 | 無此欄位不得進入 WBS | 見 WBS 表 |
| 驗收命令必可重跑 | `cargo test -p X`、`cargo clippy -- -D warnings`、`cargo fmt --check` | 非「測試通過」主觀描述 |
| DoR（Definition of Ready） | 任務開始前：需求清楚、測試環境就緒、依賴已解決 | — |
| DoD（Definition of Done） | 任務完成後：程式碼入庫、測試通過、文件更新、CI 綠燈 | — |

### 5.3 品質閘門命令（Quality Gates）

| 專案類型 | 命令 | 退出標準 |
|---|---|---|
| Rust（所有） | `cargo fmt --all -- --check` | exit 0 |
| Rust | `cargo clippy --workspace --all-targets -- -D warnings` | exit 0 |
| Rust | `cargo test --workspace --no-fail-fast` | 0 failed |
| Rust（Windows 4551） | `$env:CARGO_TARGET_DIR="$env:LOCALAPPDATA\Temp\flaps-target"; cargo ...` | 同上 |
| Python | `pytest --cov --cov-fail-under=80` | exit 0 |
| HTML/Markdown | `markdownlint` / `html-validate` | 0 error |

### 5.4 分支與提交規範（Git）

- **分支命名**：`feature/<issue-id>-<short-desc>`、`fix/<issue-id>-<short-desc>`、`docs/<short-desc>`、`chore/<short-desc>`。
- **提交訊息**：`<type>: <subject>`（type: feat/fix/docs/refactor/test/chore/perf）。Conventional Commits。
- **每日備份**：無 remote 的專案（re-toolchain、oekap）每日執行 `git bundle create backup-YYYYMMDD.bundle --all` 並複製至 `archive/`。
- **PR 規則**：必須有描述、測試結果、review 簽核；CI 綠燈後方可合併。

### 5.5 Code Review 規則

- 任何 PR 必須至少 1 人 review（本環境：自己 review + QA 驗證）。
- Review 重點：功能正確性、安全性（無 secret、無 SQL injection）、測試覆蓋、文件同步。
- 不得 approve 自己的 PR（即使 solo）— 必須經過 QA 簽核或 24 小時冷卻。

| G0 啟動 | 專案憲章、OQ 登記冊、範圍確認單 | OQ ≥ 80% 回覆、利害關係人簽署 | Gate 1 |
| G1 需求 | FRS（FR/NFR/MoSCoW）、claims-vs-evidence | FRS 簽核、驗收標準可量測 | Gate 1 |
| G2 設計 | 架構文件、ADR、介面矩陣、安全規範 | ARCH/SEC 簽核、無高風險缺陷 | Gate 2 |
| G3 開發 | 程式碼入庫、單元測試報告 | 覆蓋率 ≥ 80%、clippy/fmt 0 錯 | Gate 3 |
| G4 測試 | 整合測試報告、效能/安全報告、UAT 簽核 | 效能達標、差異率 ≤ 0.5% | Gate 4 |
| G5 部署 | 部署手冊、回滾演練、監控啟動 | 首週一致性 ≥ 99.5% | Gate 5 |
| G6 結案 | 移交文件、維運手冊、結案報告、Knowledge 條目 | OPS 簽收、知識沉澱完成 | Gate 6 |

### 6.2 結案流程（Closure）

1. **移除假完成標記**：status ledger → Done；文件 status → Superseded/Archived。
2. **知識沉澱**：至少 3 條 ADR 或 Knowledge 條目（教訓、決策、可重用模式）。
3. **封存**：所有產出移入 `archive/<project>/`；保留 SHA256 校驗。
4. **回顧**：Post-mortem 報告（目標達成度、經驗教訓、後續建議）。

### 6.3 首個套用範例：RPA-ECOM

- 當前階段：G1（需求與 OQ）→ Phase 1 啟動（T0 = 2026-11-02）。
- 閘門條件：M1（11-16）FRS 簽核、OQ ≥ 80% 回覆；M2（11-30）設計評審；B-01/B-05 ADR 會簽。
- 退出 G1 標準：FRS 簽核 + OQ 至少 80% 正式回覆 + 利害關係人簽署範圍確認單。

## 7. 文件管理（Document Management）

### 7.1 分類體系（Classification）

| 代碼 | 類別 | 範例 | 儲存路徑 |
|---|---|---|---|
| P | Project（專案憲章、WBS、時程） | 專案憲章、WBS 表、甘特圖 | `docs/project/` |
| D | Design（架構、介面、資料模型） | 架構文件、ADR、介面矩陣 | `docs/architecture/`, `docs/contracts/` |
| V | Verification（測試報告、UAT、品質） | 單元/整合/效能測試報告、UAT 簽核 | `docs/quality/` |
| R | Risk（風險登記冊、問題清單） | 風險登記冊、OQ 清單 | `docs/quality/` |
| L | Life（維運手冊、部署手冊、SOP） | 部署手冊、維運手冊、操作手冊 | `docs/operations/` |
| C | Compliance（資安、法遵、稽核） | 滲透測試、稽核報告 | `docs/quality/` |

### 7.2 狀態機（Status Machine）

```
Draft → Review → Approved → (Superseded → Archived)
```

- **Draft**：作者編輯中；不得引用為證據。
- **Review**：送審中；reviewer 簽核或退回。
- **Approved**：正式生效；可作為證據。
- **Superseded**：已被新版取代；保留供稽核。
- **Archived**：移入 `archive/<project>/`；不再流通。

### 7.3 強制規則（Mandatory Rules）

1. **唯一現行版**：每份文件僅一份 Approved 版本；舊版必須標 Superseded 或移入 archive。
2. **命名規範**：`<專案代碼>_<文件類型>_<版本>.<ext>`，例如 `FLAPS-RPA-ECOM-2026_FRS_v1.0.md`。版本號：vMajor.Minor.Patch。
3. **修訂紀錄**：每份文件必須含 §修訂紀錄表（版本、日期、變更摘要、作者）。
4. **來源檢索日期**：所有外部參考必須附檢索日期（例如 "檢索日期 2026-11-01"）。
5. **不實宣稱零容忍**：能力宣稱必須指向測試 ID／命令／快照（claims-vs-evidence 規則）；違反者降級為 Draft 並修正。
6. **修正包機制**：文件修正必須走修正包腳本模式（逐項替換 + 計數驗證 + SHA256），參考 RPA v2.1 修正包（54 項全過）。

### 7.4 封存規則（Archiving）

- 封存目錄：`archive/<project>/` 或 `archive/legacy-root/`。
- 封存前：計算 SHA256 並記錄於 `archive/SHA256_MANIFEST.txt`。
- 封存後：原位置保留指標（`SUPERSEDED → see archive/...`）或移除。

## 8. 知識管理（Knowledge Management）

### 8.1 知識庫結構標準

```
Knowledge/
├── traceability/     # claims-vs-evidence, field-to-code, vr-to-test
├── uat/              # UAT-REPORT.md（誠實標示執行狀態）
├── updates/          # KUP-NNN-*.md（修訂追蹤）
├── decisions/        # ADR 全域註冊表（跨專案索引）
├── lessons/          # 教訓登記冊（L-NNN）
├── sources/          # 原始來源快照（PDF/DOCX/網頁）
└── tools/            # build.ps1、dev-env、驗證腳本
```

### 8.2 宣稱-證據通則（Claims-vs-Evidence Rule）

- 每項能力宣稱必須指向：測試 ID、可執行命令、或來源快照（三者擇一）。
- 無法佐證者 → 標 `unverified` 或刪除；不得以「據了解」「一般而言」保留。
- 撤回是允許的處置，撤回後必須同步更新對外文件。

### 8.3 決策日誌（ADR Registry）

- 全域 ADR 註冊表：`Knowledge/decisions/ADR_REGISTER.md`（索引所有專案 ADR）。
- 命名：`ADR-NNNN-<short-desc>.md`（專案內）；`ADR-<PROJECT>-NNN`（跨專案引用）。
- 每個 ADR 必含：Status、Context、Options、Decision、Consequences、Evidence、Owner、Due Date。
- 未核准的 ADR 必須標 `Draft`，不得作為實作依據。

### 8.4 教訓登記（Lessons Learned）

- 格式：`L-NNN-<title>.md`，含：現象、根因、影響、修正、預防措施、適用範圍。
- 範例（本組合已有）：Mutex 測試失敗（L-001）、4551 封鎖（L-002）、Mermaid 宣稱失實（L-003）。
- 每個 Gate Review 必須回顧至少 1 條教訓。

### 8.5 知識維護節奏

| 頻率 | 活動 | 產出 |
|---|---|---|
| 每週 | claims-vs-evidence 更新（新增/變更宣稱先加列再寫文件） | claims-vs-evidence.md |
| 每月 | ADR 註冊表同步、來源快照歸檔 | ADR_REGISTER.md |
| 每季 | 知識庫清理（過期條目標 Superseded） | 清理報告 |
| 每閘門 | 教訓登記（至少 1 條） | L-NNN |

## 9. 生產與開發管理（Production & Development Management）

### 9.1 環境三級分離

| 環境 | 用途 | 規格 | FlapsErp 路徑 | 資料隔離 |
|---|---|---|---|---|
| DEV | 需求開發、單元測試 | Windows 10/11, 8GB RAM, 2 核 | 測試版 | 生產資料不得回填 |
| UAT | 整合測試、驗收 | 與生產同規格 | 穩定版 | 同上 |
| PROD | 實際對接 | Windows 10/11 或 Server, 16GB, 4 核, 固定 IP | 發行版 | — |

### 9.2 建置標準（Windows App Control 4551 解）

- **所有 Rust 建置產物必須置於** `%LOCALAPPDATA%\Temp\` 下（例如 `C:\Users\<user>\AppData\Local\Temp\flaps-target`）。
- **統一使用 `build.ps1`**（Wellfit 已實作）：`powershell -ExecutionPolicy Bypass -File "scripts/build.ps1" -Command "..."`。
- **.cargo/config.toml** 必須設定 `target-dir = ...`（相對路徑或環境變數）。
- **禁止直接在 Desktop/專案目錄下執行 cargo build**（4551 封鎖）。
- **新成員入職**：第一步驗證 `build.ps1` 可在 Temp 路徑成功建置。

### 9.3 發布管理（Release Management）

- **版本號**：`vMajor.Minor.Patch`（例如 v1.0.0），由 `git tag` 管理。
- **發布流程**：DEV → UAT（整合/效能/安全測試）→ PROD（離峰時段 02:00~06:00 部署）→ 冒煙測試 → 監控。
- **回滾**：停止 Windmill 排序 → 還原最近備份 → 重新部署前一版 → 驗證 → 重新啟動。RTO ≤ 4h，RPO ≤ 24h。
- **Git Tag**：每次發布打 tag（Wellfit 目前 v1.0.2 ~ v1.0.14）；Tag 訊息含變更摘要。

### 9.4 測試管理（Test Management）

| 層級 | 責任 | 退出條件 |
|---|---|---|
| 單元測試 | DEV | 覆蓋率 ≥ 80%，無 Severity 1/2 缺陷 |
| 整合測試 | QA | 所有介面測試通過，幂等與對帧邏輯正確 |
| 系統測試 | QA | 端對端業務流程 100% 通過 |
| 效能測試 | QA | API ≤ 5s、UI ≤ 30s、日處理量 ≥ 200 筆 |
| 安全測試 | QA/SEC | 敏感欄位遮蔽 100%，無高危險漏洞 |
| UAT | BIZ-ERP/BIZ-ECOM | 業務負責人簽署 UAT 驗收單 |

**#[ignore] 測試規則**：標記 ignore 的測試必須附註原因（例如 4551 封鎖）；每次 CI 必須執行 `--ignored` 一遍；若 ignore 原因消失（如 4551 已修復），必須移除 ignore。

## 10. 研究管理（Research Management）

### 10.1 研究型專案（R 型）管理規則

| 規則 | 說明 |
|---|---|
| 時間盒（Time-box） | 研究任務必須設定時間盒（≤ 2 週）；到期未完成則評估退出或延長（需 ADR） |
| 期望產出 | 研究必須產出「三件套」：(1) 研究報告（FACT/INFERENCE 分離）、(2) 規格文件、(3) 決策建議（ADR） |
| 退出規則 | 研究結束後必須做出決策：升級為 P 型（產品化）、併入既有系統、或封存（archive） |
| 禁止幽靈產物 | 未使用的 PoC/實驗程式碼必須封存或刪除；不可留在主分支 |

### 10.2 研究報告模板（FACT/INFERENCE 分離）

- **FACT**：可驗證的客觀事實（來源、測試結果、文件原文）。
- **INFERENCE**：基於 FACT 的推論（需標註風險等級與驗證方式）。
- **ASSUMPTION**：待驗證的假設（需列明驗證方式與風險等級）。
- **CONSTRAINT**：不可違反的邊界條件。

### 10.3 現有案例處置

| 專案/模組 | 類型 | 處置方案 |
|---|---|---|
| Flaps root（core/platform/web） | R 型原型 | 補提 R 型豁免 ADR（§3.4）；或重構為 P 型（需通過 G1-G6） |
| re-toolchain experiments | R 型 | 建立 `experiments/README.md` 說明每個實驗的狀態（active/concluded/archived） |
| agentre-bench version2/version3 | R 型混亂 | 選定一個版本為主線，封存其餘至 `archive/bench-v2/`、`archive/bench-v3/` |
| Wellfit platform/tests/{e2e,soak} | 幽靈產物 | 從未編譯 → 刪除或移入 `tests/pending/` 並在 WBS 中排入 G4 |

## 11. 其他管理面向（Other Management Dimensions）

### 11.1 需求管理（Requirements Management）

- **需求 ID 体系**：FR-01~NN（功能）、NFR-01~NN（非功能）、OQ-01~NN（待確認問題）。
- **MoSCoW 分類**：Must/Should/Could/Won't，工期佔比 60/25/10/5%。
- **OQ 登記冊**：所有待確認問題必須有 owner + due date + 升級路徑（RSK-07： vendor 配合度不足）。
- **需求追蹤矩陣**：FR → 設計 → 測試 → 驗收，100% 對應。

### 11.2 風險管理（Risk Management）

| 層級 | 頻率 | 產出 | 負責 |

### 11.3 變更管理（Change Management）

- 變更申請模板見附錄 T-06。

### 11.4 利害關係人與溝通（Stakeholder Communication）

- 所有外部依賴（vendor API、沙盒憑證、表頭規格）必須登記於 OQ 登記冊。
- 每週追蹤；延遲 > 2 週啟動備援方案（Fiddler/Process Monitor 擷取、替代供應商）。
- 當前 critical 依賴：OQ-E3（銀行沙盒）、OI-003（蝦皮表頭）、OI-018（UAT 資料）、MTRIX-030（MTRIX 議題負責人）。

### 11.6 資安與法遵（Security & Compliance）

- 傳輸層 TLS 1.2+；API 金鑰儲存於 Windows 認證管理員或環境變數；敏感欄位遮蔽率 100%。
- 本機儲存加密（AES-256）；稽核日誌保留 ≥ 1 年。
- PowerShell 執行原則：AllSigned（v2.1 已修正）。
- 程式碼註解覆蓋率 ≥ 80%；RPA 工作流模組化（≤ 500 行/模組）。
- 所有變更必須經過 Code Review 與 QA 簽核後方可合併至主分支。

### 11.7 成本與授權（Cost & Licensing）

- **授權成本為零**：優先使用開源工具（OpenRPA MPL-2.0、Windmill、PostgreSQL、Rust 生態）。
- **預算估算**：RPA 專案 58~101 人日（WBS 重算後）；Wellfit 由 Cargo.lock 固定版本。
- **成本追蹤**：每月報告預算消耗；若超支 > 10% 啟動變更管理。

- 改善行動（CI-NNN）登記於 `Knowledge/lessons/` 或 `docs/management/improvement_log.md`。
- 每項改善行動：描述、負責人、due date、驗證方式、狀態。
- 每季 QBR 檢討所有 CI-NNN 狀態。

- 本文件（MOP v1.0）為活文件，修訂走：變更申請 → 影響評估 → 核准 → 實作 → 驗證。
